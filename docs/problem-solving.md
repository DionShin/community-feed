# 문제 해결 기록

개발하면서 발견한 문제와 해결 과정을 기록함. 각 항목은 문제, 원인, 검토한 해결책, 선택과 이유, 결과, 남은 과제 순서로 적음. 숫자는 모두 직접 측정하거나 테스트로 확인한 값임.

## 1. 인기 피드 응답 시간이 이벤트 수에 비례해 늘어남

> 진행 상황: 1~3차 개선 완료. 단건 응답 시간은 이벤트 100만 개 기준 980ms → 103ms. 동시 연결 50개에서는 초당 처리 요청 28 → 1,345.

### 상황
인기 피드는 요청이 올 때마다 최근 24시간의 행동 이벤트(조회, 공감, 댓글)를 글별로 집계해 점수순으로 보여줌. 가장 단순하고 결과가 항상 최신인 방식으로 먼저 구현했음.

### 문제 발견
테스트 데이터를 늘려가며 응답 시간을 측정했음.
- **측정 환경:** 로컬 MongoDB 7.0(WiredTiger), Ryzen 5 7500F, 메모리 32GB. 크기마다 3회 예열 후 20회 측정.
- **테스트 데이터:** 유저 5천 명, 글 2만 개, 7일치 이벤트. 소수의 인기글과 헤비 유저에 행동이 몰리도록 지프 분포로 생성했고, 이벤트 종류는 노출 70%, 조회 22%, 댓글 3%, 공감 4.5%, 공감 취소 0.5%로 구성했음. 같은 시드를 써서 매번 같은 데이터로 비교함.
- 측정 스크립트: `scripts/bench-popular.js`, 원본 결과: `bench-results/`

| 전체 이벤트 | 24시간 내 이벤트 | 중앙값 | p95 | 읽은 문서 수 |
|---|---|---|---|---|
| 10만 | 42,166 | 82ms | 92ms | 42,166 |
| 30만 | 126,352 | 257ms | 292ms | 126,352 |
| 100만 | 421,378 | 980ms | 1,099ms | 421,378 |
| 300만 | 1,264,715 | 3,487ms | 6,830ms | 1,264,715 |

응답 시간이 24시간 내 이벤트 수에 거의 정비례해 늘었음. 이벤트 100만 개에서 인기 탭을 한 번 여는 데 약 1초가 걸렸음.

### 원인 분석
실행 계획(explain)으로 확인했음.
1. **인덱스는 쓰고 있었음.** 수신 시각 인덱스로 24시간 범위를 정확히 찾아갔다(IXSCAN).
2. **범위 안의 이벤트를 전부 읽었음.** 읽은 문서 수가 24시간 내 이벤트 수와 정확히 같았음. 인덱스는 어디를 읽을지 알려줄 뿐, 범위 안의 양을 줄이지는 못함.
3. **문서 본체를 꺼내는 비용이 더해졌다(FETCH).** 인덱스에는 수신 시각만 있어서, 이벤트 종류와 글 id를 알려고 문서를 하나씩 읽었음.
4. **점수에 쓰지 않는 노출 이벤트까지 범위 안에서 함께 읽혔음.** 노출은 전체 이벤트의 70%다.
5. **요청마다 같은 계산을 반복했음.** 순위는 몇 초 사이에 거의 바뀌지 않는데, 요청 수만큼 전체를 다시 읽음.

### 검토한 해결책
| 후보 | 기대 효과 | 한계 |
|---|---|---|
| A. 커버링 인덱스 | 문서 본체를 읽지 않음 | 범위 전체를 훑는 비례 구조는 그대로 |
| B. 결과 캐시 | 두 번째 요청부터 즉시 응답 | 느린 계산을 숨길 뿐, 캐시가 비면 누군가는 기다림 |
| C. 시간 단위 사전 집계 | 읽을 양이 "이벤트 수"에서 "활동한 글 수 × 24시간"으로 줄어듦 | 통계 갱신 작업이 필요하고 이벤트와 어긋날 수 있음 |
| D. 순위 스냅샷 | 요청 비용이 데이터 양과 무관 | 순위가 몇 분 늦고, 계산 작업은 여전히 무거움 |

비용이 거의 없는 A로 인덱스의 한계를 먼저 확인하고, C로 비례 구조 자체를 바꾸기로 했음. B는 느린 계산을 고치지 않고 가리는 방법이라 C 이후에 필요하면 붙임.

### 1차 개선: 커버링 인덱스와 필드 순서
집계에 필요한 필드(종류, 수신 시각, 글 id)를 모두 담은 인덱스를 만들었음. 필드 순서에 따라 결과가 달라질 것으로 보고 두 순서를 모두 측정했음.

| 전체 이벤트 | 기존 `{receivedAt}` | `{receivedAt, type, postId}` | `{type, receivedAt, postId}` |
|---|---|---|---|
| 10만 | 82ms | 56ms | **23ms** |
| 30만 | 257ms | 171ms | **65ms** |
| 100만 | 980ms | 532ms | **206ms** |
| 300만 | 3,487ms | 1,545ms | **525ms** |

표의 값은 중앙값임. 300만 개에서 p95는 6,830ms에서 631ms로 줄었음.

| 이벤트 300만 개 기준 | 기존 | 시각 우선 | 종류 우선 |
|---|---|---|---|
| 실행 계획 | IXSCAN → FETCH | IXSCAN만(커버링) | IXSCAN만(커버링) |
| 읽은 인덱스 키 | 1,264,715 | 1,260,009 | 379,006 |
| 읽은 문서 | 1,264,715 | 0 | 0 |

- **커버링 효과:** 두 순서 모두 문서를 하나도 읽지 않게 되었음. 시각 우선 순서만으로 응답 시간이 약 절반이 되었음.
- **필드 순서 효과:** 시각 우선 순서는 24시간 범위의 키를 전부 훑은 뒤 인덱스 안에서 노출 이벤트를 버렸음. 종류 우선 순서는 종류별로 범위를 따로 찾아가서, 노출 이벤트의 키를 아예 읽지 않았음. 같음 조건을 앞에, 범위 조건을 뒤에 두는 ESR 규칙이 실측으로 확인되었음.
- 최종적으로 `{type, receivedAt, postId}`를 채택했고, 대체된 `{receivedAt}` 인덱스는 이벤트 저장 비용만 늘리므로 삭제했음.

### 1차 개선의 결과와 한계
- 이벤트 100만 개 기준 중앙값 **980ms → 206ms (약 4.7배)**, 300만 개 기준 **3,487ms → 525ms (약 6.6배)**.
- 그러나 응답 시간은 여전히 이벤트 수에 비례해 늘어난다(10만 개 23ms → 300만 개 525ms). 범위 안의 키를 전부 훑는 구조가 그대로이기 때문임. 인덱스는 상수배 개선이고, 근본 해결은 읽는 양 자체를 줄이는 2차 개선(사전 집계)에서 다룸.
- 아직 동시 요청 상황은 측정하지 않았음.

### 2차 개선: 시간 단위 사전 집계
글별, 시간별 통계 컬렉션(`post_stats_hourly`)을 만들고, 인기 피드는 최근 24칸만 더하도록 바꿨음. 인기글 하나에 이벤트가 1만 개 있어도 24시간 통계는 최대 24줄임.

**통계 갱신 방식.** 세 가지를 비교했다(자세한 비교는 설계 결정 기록 10번).
- 쓰기 시점 증가: 항상 최신이지만, 이벤트마다 쓰기가 두 번이고 같은 이벤트를 두 번 처리하면 숫자가 틀어짐.
- Change Stream 구독: 거의 실시간이지만, 재시작 시 중복 처리와 재시작 위치 관리가 필요함.
- **주기적 재계산(채택):** 1분마다 직전 시간과 현재 시간 칸을 원본 이벤트로 다시 계산해 통째로 덮어씀. 몇 번을 실행해도 결과가 같고, 늦게 저장된 이벤트도 다음 실행에서 반영됨. 원본 이벤트가 정답이고 통계는 언제든 다시 만들 수 있는 사본임.

**정확성 검증.** 기준 시각이 정각이면 두 방식의 집계 기간이 정확히 같음. 모든 측정에서 통계 방식의 상위 20개 글과 점수가 원본 이벤트 방식과 일치했음. 같은 내용을 통합 테스트로도 고정했음.

**결과.** 인기 피드 응답 시간 중앙값을 단계별로 비교했음.

| 전체 이벤트 | 기존 | 1차: 커버링 인덱스 | 2차: 시간별 통계 |
|---|---|---|---|
| 10만 | 82ms | 23ms | **18ms** |
| 30만 | 257ms | 65ms | **45ms** |
| 100만 | 980ms | 206ms | **103ms** |
| 300만 | 3,487ms | 525ms | **208ms** |

| 이벤트 300만 개 기준 | 기존 | 1차 | 2차 |
|---|---|---|---|
| 읽은 항목 수 | 문서 1,264,715개 | 인덱스 키 379,006개 | 통계 문서 70,412개 |
| p95 | 6,830ms | 631ms | 218ms |

- 이벤트 100만 개 기준 **980ms → 103ms (약 9.5배)**, 300만 개 기준 **3,487ms → 208ms (약 16.8배)**. 1차 개선 대비로는 각각 약 2.0배, 2.5배.
- **비용 구조가 바뀌었음.** 24시간 내 이벤트가 30배 늘 때(42,166 → 1,264,715) 읽는 통계 문서는 12.6배(5,596 → 70,412), 응답 시간은 11.4배 늘었음. 읽는 양이 이벤트 수가 아니라 "24시간 안에 활동이 있었던 (글, 시간) 칸 수"를 따름. 이 값은 글 수 × 24를 넘을 수 없음.

**대신 치르는 비용.** 계산이 사라진 것이 아니라 요청 경로에서 백그라운드 작업으로 옮겨졌음.

| 전체 이벤트 | 1분마다 실행하는 통계 갱신 | 서버 시작 시 전체 채우기 |
|---|---|---|
| 10만 | 21ms | 157ms |
| 30만 | 49ms | 440ms |
| 100만 | 128ms | 1,079ms |
| 300만 | 271ms | 2,523ms |

- 통계 갱신 비용은 요청 수와 무관하게 1분에 한 번임. 1차 개선 방식은 요청마다 집계했으므로, 요청이 많을수록 차이가 커짐.
- 인기 순위가 최대 1분 늦음.
- 정각이 아니면 집계 기간이 최대 25시간이 됨.
- 직전 시간보다 오래된 칸은 확정으로 보므로, 아주 늦게 저장된 이벤트는 전체 다시 채우기 전까지 반영되지 않음. 이 동작도 테스트로 고정했음.

2차 개선 직후에도 요청 경로에 이벤트 300만 개 기준 약 200ms가 남아 있었음.

### 3차 개선: 통계 버전 기준 결과 캐시
**왜 이제 캐시인가.** 처음에는 캐시를 "느린 계산을 가리는 수단"으로 보고 미뤘음. 사전 집계 이후에는 통계가 1분마다만 바뀌므로, 같은 통계로 계산한 순위는 다음 갱신 전까지 그대로임. 이때 캐시는 "같은 결과를 반복 계산하지 않는 수단"이 되고, 이미 감수한 1분 지연 외에 새로운 지연을 만들지 않음.

**캐시를 비우는 기준.** 시간 기준(60초 보관)은 통계 갱신 직전에 만든 캐시가 갱신 후에도 최대 60초 더 남음. 그래서 통계 갱신이 끝날 때마다 버전 번호를 올리고, 캐시는 만들어진 시점의 버전이 현재와 같을 때만 쓰게 했음. 다른 서버가 통계를 바꾸거나 갱신 작업이 멈춘 경우를 대비해 2분이 지나면 무조건 다시 계산함.

**캐시 쇄도 방지.** 캐시가 빈 순간 요청이 몰리면 모두 계산을 시작할 수 있음. 같은 버전을 계산 중인 작업이 있으면 새 요청은 그 결과를 함께 기다리게 했음. 테스트에서 동시 요청 20개가 계산 한 번을 공유하는 것을 확인했음.

**Redis를 쓰지 않은 이유.** 서버가 한 대라 서버 메모리로 충분함. 서버가 여러 대가 되어도 각 서버가 자기 통계 갱신 직후 한 번씩만 계산하므로 공유 캐시가 꼭 필요하지 않음.

### 동시 요청 측정
요청을 하나씩 보내던 측정과 달리, 실제 앱 서버에 동시 연결 50개로 10초간 인기 피드 요청을 계속 보냈다(`scripts/bench-load.js`, autocannon 사용, 운영 모드, 이벤트 100만 개).

| 방식 | 초당 처리 요청 | p50 | p99 | 인기 순위 계산 횟수 |
|---|---|---|---|---|
| 1차: 원본 이벤트 집계(커버링 인덱스) | 28 | 1,507ms | 3,058ms | 278 |
| 2차: 시간별 통계 | 63 | 719ms | 1,419ms | 626 |
| 3차: 시간별 통계 + 결과 캐시 | **1,345** | **35ms** | **49ms** | 1 |

- **동시 요청에서는 단건 측정보다 훨씬 나빠짐.** 1차 방식은 단건으로 206ms였지만, 동시 연결 50개에서는 요청들이 DB 작업을 서로 기다리며 p50이 1.5초가 되었음. 요청마다 무거운 계산을 하는 구조는 "데이터 양 × 요청 수"로 비용이 커짐.
- **3차 방식은 2차 대비 초당 처리량 약 21배, 1차 대비 약 48배.** 10초 동안 13,450건을 처리하면서 인기 순위 계산은 한 번만 했음.

### 측정 중 발견한 렌더링 병목
캐시를 적용했는데도 작은 데이터에서 요청당 CPU 시간이 예상보다 컸음. 원인은 두 가지였음.
1. **개발 모드에서는 Express가 화면 템플릿을 캐시하지 않음.** 요청마다 템플릿을 다시 컴파일함. 측정은 운영 모드로 하도록 바꿨음.
2. **날짜 표시 함수가 호출마다 지역화 포맷 객체를 새로 만들었음.** 직접 재보니 `toLocaleString`은 호출당 약 0.05ms, 포맷 객체를 재사용하면 약 0.001ms였음. 피드 한 페이지에서 20번 이상 호출하므로 페이지당 약 1ms가 줄었음. 출력 문자열은 이전과 같음.

짧은 사전 측정(이벤트 2만 개, 연결 10개, 2초)에서 캐시 방식의 초당 처리량이 운영 모드 전환 후 545, 날짜 포맷 수정 후 1,405였음. 측정 시간이 짧아 참고값으로만 기록함.

### 남은 과제
- 통계 조회는 문서 본체를 읽는다(FETCH). 캐시 덕분에 1분에 한 번이라 우선순위가 낮음.
- 서버가 여러 대가 되면 각 서버가 같은 통계 갱신을 반복함. 별도 작업 프로세스나 잠금이 필요함.
- 인기 순위는 최대 1분 늦음. 실시간성이 필요해지면 Change Stream 구독과 이벤트 id 기반 중복 제거를 검토함.

## 2. 동시 요청에서 생기는 중복과 숫자 어긋남

### 문제
같은 요청이 동시에 여러 번 들어오면 데이터가 틀어질 수 있는 지점이 세 곳 있었음.
- 같은 아이디로 동시에 가입하면 중복 계정이 생길 수 있음.
- 공감 버튼을 연타하면 공감 수가 실제보다 커질 수 있음.
- 같은 댓글의 삭제 요청이 겹치면 댓글 수가 여러 번 줄어들 수 있음.

### 원인
"먼저 조회하고 없으면 저장"하는 방식은 조회와 저장 사이에 다른 요청이 끼어들 수 있음. 동시에 온 요청 여러 개가 모두 "없음"을 확인하고 저장함. 또 요청이 올 때마다 숫자를 올리면, 실제 상태 변화와 무관하게 숫자가 움직임.

### 해결
1. **중복은 DB의 고유 인덱스로 막았음.** 아이디, (글, 유저) 공감 쌍에 고유 인덱스를 걸고, 조회 없이 바로 저장을 시도함. 중복 키 에러가 나면 "이미 있는 상태"로 처리함.
2. **숫자는 상태가 실제로 바뀐 경우에만 움직이게 했음.** 공감 문서가 새로 생겼을 때만 +1, 실제로 지워졌을 때만 -1 함. 댓글 삭제도 삭제 표시가 실제로 바뀐 요청 하나만 댓글 수를 내림.
3. **공감 API를 멱등하게 만들었음.** 공감은 PUT(공감한 상태로 만들기), 취소는 DELETE(공감하지 않은 상태로 만들기)다. 같은 요청을 여러 번 보내도 결과가 같음.

### 결과
동시 요청 테스트로 확인했음.

| 상황 | 결과 |
|---|---|
| 같은 아이디로 가입 요청 5개를 동시에 보냄 | 1개만 성공, 4개는 409 |
| 한 사람이 공감 요청 10개를 동시에 보냄 | 공감 문서 1개, 공감 수 1 |
| 8명이 동시에 공감 | 공감 수 8 |
| 공감하지 않은 글에 취소 요청 3개를 동시에 보냄 | 공감 수 0, 음수 아님 |
| 같은 댓글 삭제 요청 5개를 동시에 보냄 | 댓글 수가 한 번만 줄어듦 |

### 남은 과제
공감 문서 저장과 공감 수 증가는 별개의 쓰기 두 번임. 그 사이에 서버가 죽으면 두 값이 어긋날 수 있음. 어긋남을 찾는 검사 스크립트를 만들고, 트랜잭션과 주기적 재계산을 비교할 예정임.

## 3. 학습용 코드의 권한 검사와 입력 검증 부재

### 문제
처음 학습하며 만든 게시판 코드를 분석하다 다음 문제를 발견했음.
- 글 수정 API에 작성자 확인이 없어 누구나 남의 글을 수정할 수 있었음.
- 로그인하지 않고 글을 쓰면 서버 에러(500)가 났음.
- 형식이 틀린 글 id로 접속하면 서버 에러(500)가 났음.
- 글 삭제를 기다리지 않고 "삭제 완료"를 응답해, 실패해도 성공으로 보였음.
- 댓글 작성자 id를 존재하지 않는 필드에서 읽어, 매번 엉뚱한 id가 저장되었음.
- 로그인 실패 메시지가 "아이디 없음"과 "비밀번호 불일치"로 달라, 가입된 아이디를 알아낼 수 있었음.
- 채팅 요청을 누를 때마다 같은 두 사람의 채팅방이 새로 생겼음.
- 채팅 소켓에 로그인 확인이 없어, 방 id만 알면 누구나 남의 방에 들어가 메시지를 보낼 수 있었음.
- 채팅 메시지를 저장하지 않아 새로고침하면 대화가 사라졌고, 받은 메시지를 HTML로 그대로 넣어 XSS 위험이 있었음.
- 새 글 실시간 알림이 접속자마다 Change Stream을 열려는 구조였고, 받은 제목을 HTML로 그대로 넣었음.

### 해결
- 수정과 삭제 전에 글을 읽어 없으면 404, 남의 글이면 403을 돌려줌. 실제 수정 쿼리 조건에도 작성자 id를 한 번 더 걺. 확인과 수정 사이에 다른 요청이 끼어들 수 있기 때문임.
- 로그인이 필요한 경로에 공통 미들웨어를 붙였음. 화면 요청은 로그인 페이지로, API 요청은 401 JSON으로 응답함.
- URL의 id가 24자리 16진수인지 먼저 검사해, 형식이 틀리면 404로 처리함.
- 에러를 두 종류로 나눴음. 사용자에게 보여줘도 되는 에러는 메시지를 그대로 보여주고, 예상하지 못한 에러는 내용을 숨기고 로그에만 남김.
- 로그인 실패 메시지를 하나로 통일했음.
- 채팅방은 (글, 문의자) 조합에 고유 인덱스를 걸고 "있으면 그대로, 없으면 생성"을 한 번의 쿼리로 처리했음. 동시에 문의해도 방은 하나임.
- 채팅 소켓은 HTTP와 같은 세션 미들웨어로 연결 시점에 로그인을 확인하고, 방에 들어갈 때마다 참여자인지 DB로 확인함. 메시지는 저장을 마친 뒤에만 방에 전달함.
- 메시지와 알림은 화면에 글자로만 넣는다(textContent).
- 새 글 알림은 서버당 Change Stream 하나로 바꿨다(설계 결정 기록 13번).

### 결과
통합 테스트로 확인했음. 남의 글 수정과 삭제는 403을 받고 DB 내용이 바뀌지 않음. 잘못된 id와 없는 id는 404, 비로그인 글쓰기는 로그인 페이지로 이동함. 제목에 스크립트를 넣으면 화면에 글자로만 보임. 같은 글에 동시에 5번 문의해도 채팅방은 하나이고, 로그인하지 않은 소켓 연결과 참여자가 아닌 사람의 방 입장, 메시지 전송은 모두 거절됨.

## 4. 공개 저장소에 DB 접속 정보가 노출됨

### 문제
학습용 코드를 분석하다 MongoDB 접속 주소가 소스 코드에 그대로 적혀 공개 저장소에 올라가 있는 것을 발견했음. 주소에 DB 계정의 아이디와 비밀번호, 클러스터 주소가 모두 포함되어 있었음. 세션 암호화 키도 코드에 하드코딩되어 있었음.

### 원인
환경변수를 쓰는 코드와 하드코딩된 코드가 섞여 있었음. git은 과거 버전을 모두 보관하므로, 파일을 지워도 첫 커밋에서 비밀번호를 볼 수 있었음.

### 해결
1. DB 계정 비밀번호를 즉시 교체해 노출된 정보를 무효화했음. 이미 복사되었을 수 있으므로 히스토리 삭제보다 교체가 우선임.
2. 접속 정보와 세션 키를 모두 환경변수로 옮기고, .env는 git에서 제외했음. 저장소에는 값이 비어 있는 .env.example만 둠.
3. 필수 환경변수가 없으면 서버가 시작 단계에서 바로 실패하게 했음. 실행 중에 엉뚱한 에러가 나는 것보다 원인이 분명함.
4. 비밀번호가 남은 히스토리를 이어 쓰지 않고 새 저장소에서 시작했음.

## 5. 대용량 측정 중 인덱스 생성 실패

### 문제
이벤트 300만 개로 커버링 인덱스를 측정하던 중, 인덱스 생성이 "Illegal byte sequence" 에러로 실패했음. 필드 하나짜리 기존 인덱스로는 같은 데이터에서 문제가 없었음.

### 원인
MongoDB는 인덱스를 만들 때 정렬 메모리(기본 200MB)를 넘으면 임시 파일을 디스크에 씀. 필드 세 개짜리 인덱스는 이 한도를 넘었고, 임시 파일 경로가 한글이 포함된 Windows 사용자 폴더 아래에 있어서 파일을 열지 못했음.

### 해결
측정용 MongoDB의 인덱스 생성 메모리 한도를 2GB로 늘려 디스크에 쓰지 않고 끝나도록 했음. 측정 스크립트에만 적용되는 설정이며, 서비스 코드와 쿼리 성능에는 영향이 없음.

## 6. 테스트용 MongoDB가 기동 중 실패함: 원인을 잘못 짚었다가 다시 찾음

### 문제
테스트 파일이 늘어나던 중, 여러 테스트 파일의 테스트용 MongoDB가 시작 단계에서 내부 오류(fassert)로 실패했음. 해당 파일만 단독으로 실행하면 통과했음.

### 첫 번째 판단과 조치
Node.js 테스트 러너는 기본적으로 CPU 코어 수만큼 테스트 파일을 동시에 실행하고, 파일마다 MongoDB를 하나씩 띄움. 동시 기동에 따른 자원 경합으로 보고 동시 실행 파일 수를 4개로 제한했다(`--test-concurrency=4`). 이후 테스트가 통과했음.

### 문제 재발과 실제 원인
새 글 알림 기능을 추가한 뒤 같은 오류가 거의 모든 테스트 파일에서 다시 발생했음. 이번에는 디스크부터 확인했고, C 드라이브 여유 공간이 642MB였음. 그중 6.1GB가 성능 측정 스크립트가 남긴 임시 MongoDB 데이터였음. 측정 스크립트는 정상 종료할 때만 임시 폴더를 지우게 되어 있어서, 측정이 실패하거나 중간에 중단된 실행의 데이터가 그대로 쌓여 있었음. 첫 번째 판단 때도 이미 디스크가 부족했고, 동시 실행 수를 줄여 디스크를 덜 쓰게 되면서 우연히 통과했던 것으로 판단했음.

### 해결
1. 남아 있던 임시 데이터를 지워 6.7GB를 확보했음.
2. 측정 스크립트가 실패하거나 Ctrl+C로 중단되어도 임시 DB를 정지하고 폴더를 지우도록 정리 로직을 바꿨음. Windows에서는 DB 프로세스가 완전히 끝나기 전에 폴더를 지우면 실패하므로 재시도를 넣었음.
3. 동시 실행 제한은 테스트 실행 시 디스크와 메모리 사용을 줄이므로 유지했음.

### 배운 점
조치 후 증상이 사라졌다고 원인을 확인한 것은 아니었음. 같은 오류가 다시 나왔을 때 자원(디스크, 메모리)부터 확인하는 습관이 필요함.

## 7. 데이터 품질 검사를 만들었더니, 검사 자체가 글 수에 비례해 느려짐

### 상황
수집한 이벤트와 그 위의 통계를 믿을 수 있는지 확인하려고 데이터 품질 검사 7가지를 만들었음. 10분마다 서버 안에서 실행해 결과를 저장하고(30일 TTL), 기준을 넘으면 로그로 경고함.

| 검사 | 찾는 것 |
|---|---|
| 공감 수 어긋남 | 글의 공감 수와 실제 공감 문서 수가 다른 글 |
| 댓글 수 어긋남 | 글의 댓글 수와 삭제되지 않은 댓글 수가 다른 글 |
| 반복 조회 | 같은 사람이 같은 글을 10분 구간 안에서 반복 조회한 비율 |
| 주인 없는 이벤트 | 존재하지 않는 글을 가리키는 이벤트 비율 |
| 시계 오차 | 발생 시각과 수신 시각이 1분 넘게 차이 나는 노출 비율 |
| 통계 갱신 지연 | 시간별 통계 작업이 마지막으로 돈 뒤 지난 시간 |
| 통계 정합성 | 직전 한 시간 통계와 원본 재계산 값이 다른 글 |

### 탐지 정확도 검증
이벤트 100만 개 데이터에 개수를 정확히 아는 이상 데이터를 섞고, 섞기 전후 검사 결과의 차이를 비교했다(`scripts/bench-dq.js`). 테스트 데이터 자체에 원래 있던 반복 조회 등과 섞이지 않도록 차이로 계산했음.

| 이상 데이터 | 섞은 양 | 찾은 양 |
|---|---|---|
| 공감 수 어긋남 | 글 50개 | 50 |
| 댓글 수 어긋남 | 글 30개 | 30 |
| 반복 조회 | 5,000회 | 5,000 |
| 주인 없는 이벤트 | 2,000건 | 2,000 |
| 시계 오차 노출 | 1,000건 | 1,000 |
| 통계 불일치 | 글 10개 | 10 |

반복 조회, 주인 없는 이벤트, 시계 오차는 정확히 찾았지만 상태는 "정상"으로 남았음. 전체 대비 비율이 경고 기준(각각 20%, 1%, 5%)보다 낮았기 때문임. 탐지와 경고는 별개이고, 경고 기준은 운영하며 조정할 값임.

### 문제 발견
이벤트가 3만 개뿐인데도 공감 수, 댓글 수 검사가 각각 1초 넘게 걸렸음. 이벤트 100만 개에서도 시간이 같았음. 이벤트가 아니라 글 수에 비례한다고 보고, 이벤트 10만 개에 글 수만 바꿔 측정했음.

| 글 수 | 공감 수 검사 | 댓글 수 검사 | 전체 검사 |
|---|---|---|---|
| 2만 | 1,652ms | 1,402ms | 3,831ms |
| 10만 | 6,602ms | 7,547ms | 15,139ms |
| 20만 | 12,563ms | 14,129ms | 27,721ms |

### 원인
모든 글에 대해 공감 문서와 댓글을 하나씩 세고 있었음. 글이 수백만 개가 되면 10분마다 도는 검사가 몇 분씩 걸리게 됨.

### 해결
숫자가 어긋나는 일은 공감, 공감 취소, 댓글, 댓글 삭제가 일어나는 순간에만 생김. 반응이 없는 글의 숫자가 저절로 틀어지지는 않음. 그래서 평소 검사는 최근 24시간 안에 이런 행동 이벤트가 있었던 글만 확인하도록 바꿨음. 활동한 글 목록은 기존 `{type, receivedAt, postId}` 인덱스만으로 뽑힘. 이를 위해 댓글 삭제도 이벤트로 기록하게 했고, 동시에 같은 삭제 요청이 와도 실제로 지워진 한 번만 기록됨. 모든 글을 보는 전체 검사는 명령(`npm run dq:check -- --full`)으로 남겼음.

### 결과
같은 조건(이벤트 10만 개)에서 다시 측정했음.

| 글 수 | 확인한 글 수 (공감/댓글) | 공감 수 검사 | 댓글 수 검사 | 전체 검사 |
|---|---|---|---|---|
| 2만 | 811 / 511 | 1,652 → 58ms | 1,402 → 37ms | 3,831 → 830ms |
| 10만 | 915 / 574 | 6,602 → 68ms | 7,547 → 45ms | 15,139 → 1,107ms |
| 20만 | 896 / 631 | 12,563 → 65ms | 14,129 → 48ms | 27,721 → 1,122ms |

검사 비용이 전체 글 수가 아니라 최근 활동한 글 수를 따르게 되어, 글이 10배 늘어도 거의 변하지 않았음. 모든 크기에서 섞어 넣은 이상 데이터를 여전히 정확히 찾았음.

### 트레이드오프와 남은 과제
- 앱을 거치지 않고 DB를 직접 고쳐 생긴 어긋남은 평소 검사로 잡히지 않음. 전체 검사로만 잡힘. 이 동작을 테스트로 고정했음.
- 어긋난 숫자는 자동으로 고치지 않음. 검사 로직에 버그가 있으면 멀쩡한 데이터를 망가뜨릴 수 있어서, 고칠 목록을 먼저 보여주고 확인 후 실행한다(`npm run dq:fix-counts -- --apply`).
- 이벤트 100만 개 기준 남은 가장 비싼 검사는 주인 없는 이벤트(약 2초)다. 24시간 이벤트를 글별로 묶는 비용이라 이벤트 수에 비례함. 반복 조회도 탐지만 하고, 인기 점수에서 걸러내지는 않음.
