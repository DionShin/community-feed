# 설계 결정 기록

구현하면서 내린 주요 결정과 그 이유를 정리함. 각 항목은 검토한 대안, 선택한 이유, 감수한 단점을 함께 적음.

---

## 1. DB는 MongoDB 하나만 씀

**대안.** 유저, 게시글처럼 관계가 있는 데이터는 MySQL에, 이벤트는 MongoDB에 나눠 저장하는 방식.

**선택 이유.**
- 조인이 깊지 않음. 유저, 글, 댓글, 공감 관계가 단순함.
- 핵심 정합성 요구는 "한 사람이 한 글에 공감은 한 번"이고, 이는 고유 인덱스로 보장됨.
- 이벤트는 추가만 되고 필드가 바뀔 수 있어 스키마가 유연한 쪽이 유리함.
- 이 규모에서 DB를 둘로 나누면 운영 복잡도만 늘고 얻는 것이 적음.

**관계형 DB였다면 달라지는 점.**

| 항목 | 현재 설계 | 관계형 DB였다면 |
|---|---|---|
| 작성자 닉네임 | 글 문서에 복사 | users와 JOIN, 항상 최신 |
| 공감 수 정합성 | 두 번의 쓰기, 어긋남 위험을 검사로 확인 | 트랜잭션으로 함께 처리 |
| 공감 중복 방지 | 고유 인덱스 | UNIQUE 제약, 방식은 같음 |
| 이벤트 저장 | 필드 추가가 자유로움 | 스키마 변경 필요, 대량 데이터는 파티셔닝 |

## 2. 포함과 참조의 기준

- **별도 컬렉션으로 분리:** 댓글, 채팅 메시지, 이벤트. 끝없이 늘어나는 데이터는 문서 하나의 16MB 한계에 닿을 수 있고, 따로 페이지를 나눠 읽어야 함.
- **문서 안에 포함:** 글의 이미지 주소. 최대 3개로 개수가 정해져 있고 항상 글과 함께 읽음.
- **값을 복사(비정규화):** 글의 작성자 닉네임, 공감 수, 댓글 수. 피드 목록마다 다른 컬렉션을 조회하지 않기 위해서임.

**감수한 단점.** 닉네임을 바꾸면 예전 글에는 옛 닉네임이 남음. 지금은 닉네임 변경 기능을 두지 않는 것으로 피했음.

---

## 3. 공감 수와 댓글 수는 글 문서에 숫자로 저장함

**대안.** 피드를 그릴 때마다 likes, comments 컬렉션에서 개수를 셈.

**선택 이유.** 피드 한 페이지가 20개면 개수 조회가 20번 추가됨. 읽기가 쓰기보다 훨씬 많으므로 쓸 때 숫자를 갱신함.

**측정.** 글 20개 피드(글당 공감 5,000개, 댓글 1,000개)에서 읽을 때 세면 11ms, 쿼리 41번. 저장한 값을 읽으면 0.3ms, 쿼리 1번. 대신 공감 한 번의 쓰기가 0.233ms에서 0.465ms로 늘어남(문제 해결 기록 8번).

**정합성을 지키는 방법.** 상태가 실제로 바뀐 경우에만 숫자를 움직임. 공감 문서가 새로 생겼을 때만 +1, 실제로 지워졌을 때만 -1임. 버튼 연타나 중복 요청으로 숫자가 틀어지지 않음. 한 사람이 동시 요청 20개를 보내는 실험에서, 조회 후 저장하고 증가하는 방식은 공감 수가 평균 15.9가 됐고 채택한 방식은 100회 모두 1이었음.

**감수한 단점.** 공감 문서 저장과 숫자 증가는 별개의 쓰기 두 번임. 그 사이에 서버가 죽으면 두 값이 어긋남. 트랜잭션과 주기적 재계산 중 하나로 보완할 예정임.

## 4. 피드는 _id 커서로 페이지를 나눔

**대안.** skip과 limit을 쓰는 페이지 번호 방식.

**선택 이유.** skip 1000은 1000개를 읽고 버림. 커서 방식은 "마지막으로 본 글의 _id보다 작은 글"을 인덱스에서 바로 찾음. ObjectId 앞 4바이트가 생성 시각이라 _id 순서가 곧 작성 순서임. 다음 페이지 여부는 한 개를 더 읽어서 판단하므로 전체 개수를 세지 않음.

**측정.** 글 20만 개에서 1만 번째 페이지를 읽을 때 skip은 355.3ms, 문서 20만 개를 읽었음. 커서는 0.5ms, 문서 20개였음(문제 해결 기록 8번).

**감수한 단점.** "37페이지로 바로 이동"은 할 수 없음.

---

## 5. 글과 댓글은 삭제 표시만 함

**선택 이유.** 행동 이벤트가 글 id를 가리키고 있음. 문서를 지우면 그 기록을 해석할 수 없게 됨. 복구도 쉬움.

**감수한 단점.** 모든 조회에 "삭제되지 않음" 조건이 붙고, 데이터는 계속 쌓임. 글의 S3 이미지도 지우지 않음.

---

## 6. 이벤트는 기록 주체를 나눔

| 이벤트 | 기록 주체 | 이유 |
|---|---|---|
| 노출 | 브라우저 | 글이 실제로 화면에 보였는지는 브라우저만 앎 |
| 조회, 공감, 댓글 | 서버 | 서버가 직접 처리하므로 확실하고 조작할 수 없음 |

- 브라우저는 노출 외의 이벤트를 보낼 수 없음. 받으면 누구나 숫자를 부풀릴 수 있음. 활동 없는 글에 가짜 공감 1,000건을 보내는 실험에서, 그대로 저장하면 그 글이 1위(3,000점)가 됐고 채택한 방식은 1,000건 모두 거절했음.
- 브라우저가 보낸 노출은 종류, 글 id 형식, 화면 이름, 위치, 발생 시각을 하나씩 검사하고, 이상한 이벤트만 버림.
- 발생 시각이 하루보다 오래됐거나 5분 넘게 미래면 버림. 순위 계산에는 서버가 정한 수신 시각을 씀.

---

## 7. 이벤트 기록 실패는 사용자 요청에 영향을 주지 않음

**선택 이유.** 이벤트 기록은 부가 기능임. 기록 저장소에 문제가 생겼다고 글이 열리지 않으면 안 됨. 실패는 서버 로그에만 남김.

**감수한 단점.** 실패한 이벤트는 유실됨. 지금은 기록이 끝난 뒤 응답하므로, 기록 시간이 응답 시간에 더해짐. 이 비용은 측정 후 비동기 처리와 비교할 예정임.

---

## 8. 노출 이벤트는 "최대 한 번" 전달함

**선택 이유.** 브라우저는 노출을 모아 5초마다, 또는 20개가 쌓이면 보냄. 페이지를 떠날 때는 sendBeacon으로 보냄. 전송이 실패해도 다시 보내지 않음. 재전송하면 같은 노출이 두 번 저장될 수 있고, 이를 막으려면 이벤트 id와 중복 제거가 필요함.

**감수한 단점.** 네트워크가 불안정하면 노출 일부가 유실됨.

---

## 9. 인기 점수는 행동별 가중치의 합으로 시작함

| 행동 | 점수 |
|---|---|
| 조회 | 1 |
| 공감 | 3 |
| 공감 취소 | -3 |
| 댓글 | 5 |
| 노출 | 0 |

**근거.** 행동에 드는 노력이 클수록 관심이 강하다고 봄. 노출은 화면을 지나간 것만으로는 관심이라 볼 수 없어 제외했음. 정답이 아니라 데이터를 보며 조정할 출발점임.

**함께 정한 것.**
- 최근 24시간만 셈. 기준은 서버 수신 시각임.
- 인기 피드에는 다음 페이지가 없음. 순위가 계속 바뀌어 페이지를 넘기는 사이 같은 글이 또 나오거나 빠질 수 있음.
- 점수 상위 후보 50개에만 글 정보를 붙이고, 삭제된 글을 뺀 뒤 20개를 보여줌.

## 10. 인기 피드는 시간별 통계를 1분마다 다시 계산해 읽음

**배경.** 요청마다 원본 이벤트를 집계하면 응답 시간이 이벤트 수에 비례해 늘었음. 글별, 시간별 통계(`post_stats_hourly`)를 미리 만들어 두고, 인기 피드는 최근 24칸만 더하도록 바꿨음.

**통계 갱신 방식 비교.**

| 방식 | 장점 | 단점 |
|---|---|---|
| 쓰기 시점 증가: 이벤트를 저장할 때마다 칸의 숫자를 올림 | 항상 최신 | 이벤트마다 쓰기 두 번, 인기글 칸에 쓰기 집중, 통계만 실패하면 어긋남 |
| 주기적 재계산: 1분마다 최근 칸을 원본으로 다시 계산해 덮어씀 | 저장 경로 그대로, 멱등, 늦게 저장된 이벤트도 반영 | 최대 1분 지연, 주기마다 계산 비용 |
| Change Stream 구독: 변경 알림을 받아 숫자를 올림 | 거의 실시간 | 재시작 위치 관리 필요, 같은 이벤트를 두 번 받으면 두 번 오름 |

**선택: 주기적 재계산.**
- 원본 이벤트가 정답이고 통계는 언제든 다시 만들 수 있는 사본임. 계산 방식을 바꾸거나 통계가 깨져도 원본으로 복구됨.
- 칸 단위로 통째로 덮어쓰므로 몇 번을 실행해도 결과가 같음. 숫자를 올리는 방식은 같은 이벤트를 두 번 처리하면 틀어짐.
- 인기 순위가 1분 늦는 것은 사용자 경험에 문제가 되지 않음.

**세부 규칙.**
- 1분마다 직전 시간과 현재 시간 칸을 다시 계산함. 시각을 정한 순서와 DB에 저장된 순서가 다를 수 있어서, 조금 늦게 저장된 이벤트를 다음 실행에서 반영하기 위해서임.
- 그보다 오래된 칸은 확정된 것으로 봄. 아주 늦게 저장된 이벤트는 반영되지 않으며, 전체 다시 채우기로만 바로잡힘.
- 서버 시작 시 최근 25시간을 한 번 채움.
- 칸 단위로 자르므로, 지금이 정각이 아니면 집계 기간이 최대 25시간까지 늘어남.
- 이전 실행이 끝나지 않았으면 다음 실행을 건너뜀.

**감수한 단점.**
- 서버가 여러 대가 되면 각 서버가 같은 계산을 반복함. 결과는 덮어쓰기라 틀리지 않지만 낭비이므로, 그때는 별도 작업 프로세스나 잠금이 필요함.
- 실시간성이 필요해지면 Change Stream 구독과 이벤트 id 기반 중복 제거를 검토함.

## 11. 인기 피드 결과는 통계 버전 기준으로 캐시함

**배경.** 통계가 1분마다만 바뀌므로, 같은 통계로 계산한 순위는 다음 갱신 전까지 그대로임. 요청마다 같은 계산을 반복할 이유가 없음.

**캐시를 비우는 기준.**

| 방식 | 문제 |
|---|---|
| 시간 기준(60초 보관) | 통계 갱신 직전에 만든 캐시가 갱신 후에도 최대 60초 더 남아, 이미 감수한 1분 지연에 지연이 더해짐 |
| 통계 버전 기준(채택) | 통계 갱신이 끝날 때마다 버전을 올리고, 버전이 같을 때만 캐시를 씀. 추가 지연이 없음 |

**세부 규칙.**
- 버전이 그대로여도 2분이 지나면 다시 계산함. 다른 서버의 갱신 작업이 같은 통계를 바꾼 경우나 갱신 작업이 멈춘 경우의 안전장치임.
- 같은 버전을 계산 중이면 새 요청은 그 결과를 함께 기다림(캐시 쇄도 방지).
- 계산이 실패하면 진행 중 표시를 지워 다음 요청이 다시 시도함.

**Redis를 쓰지 않은 이유.** 서버가 한 대라 서버 메모리로 충분함. 서버가 여러 대여도 각 서버가 자기 갱신 직후 한 번씩만 계산하므로, 공유 캐시가 없어서 생기는 비용이 작음. 서버 수가 많아져 계산 부담이 커지면 그때 공유 캐시를 검토함.

## 12. 검색은 Atlas Search와 한국어 분석기를 씀

**대안.** 제목과 내용에 정규식으로 검색어를 찾는 방식.

| 항목 | 정규식 검색 | Atlas Search |
|---|---|---|
| 인덱스 | 앞부분이 고정되지 않은 정규식은 인덱스를 못 써서 글 전체를 훑음 | 검색 엔진(Lucene)이 만든 역색인을 씀 |
| 정렬 | 관련도를 알 수 없어 최신순 | 관련도 점수순, 제목 일치에 가중치 3배 |
| 한국어 | 글자가 그대로 포함되어야 찾음 | 형태소 분석기(lucene.korean)로 어미와 조사를 처리 |
| 실행 환경 | 어떤 MongoDB에서나 동작 | Atlas에서만 동작, 검색 인덱스 필요 |

**선택 이유.** 실제 데이터로 확인한 결과, 한국어 분석기는 "질문"으로 "질문이요"를, "수집하다"로 "행동이벤트 수집"을 찾았음. 정규식은 "수집하다"로 찾을 수 없음.

**세부 규칙.**
- 운영은 Atlas Search, 테스트는 정규식 검색을 씀. 인메모리 테스트 DB에는 Atlas Search가 없어서 환경변수(`SEARCH_MODE`)로 고름. 정규식 검색은 특수문자를 글자 그대로 찾도록 escape함.
- 검색 인덱스는 `npm run search:index`로 만듦. 제목과 내용만 색인함.
- 삭제된 글은 검색 인덱스에 남아 있으므로 검색 결과에서 거름.
- 결과는 상위 20개만 보여줌.

**검색 이벤트.** 검색어와 결과 개수를 이벤트로 남김. 결과가 0건인 검색어는 "찾는 사람은 있는데 없는 글"을 알려줌. 검색 결과에서의 노출과 클릭은 검색 화면 출처로 따로 기록해, 피드와 검색의 클릭률을 비교할 수 있게 했음. 검색 이벤트는 인기 점수에 넣지 않음.

**감수한 단점.** 테스트는 정규식 검색으로만 돌기 때문에, Atlas Search 쿼리 자체는 자동 테스트로 검증되지 않음. 실제 Atlas에서 직접 확인했음.

## 13. 새 글 알림은 서버당 Change Stream 하나를 SSE로 나눠 보냄

**구조.** 브라우저마다 Change Stream을 열지 않음. 서버 하나가 posts 컬렉션의 추가만 감시하는 Change Stream 하나를 열고, 연결된 브라우저 목록에 나눠 보냄. 브라우저마다 열면 접속자 수만큼 DB에 감시 커서가 생김.

**SSE를 고른 이유.** 서버에서 브라우저로 보내기만 하면 되므로 양방향인 WebSocket이 필요 없음. SSE는 일반 HTTP 응답이라 단순하고, 연결이 끊기면 브라우저가 스스로 다시 연결함.

**놓치지 않기 위한 장치.**
- 받은 변경마다 재시작 위치(resume token)를 기억함. DB 연결이 끊기면 3초 뒤 그 위치 다음부터 이어받아, 끊긴 동안 추가된 글도 전달함. DB가 보관한 변경 기록(oplog) 범위를 벗어나면 지금부터 다시 들음.
- 처음 열 때는 DB의 현재 시각부터 받도록 지정함. 감시가 실제로 시작되기까지 걸리는 시간 동안 추가된 글도 놓치지 않음. 처음에는 드라이버의 준비 완료 신호를 기다리게 만들었는데, 사용 중인 드라이버 버전이 그 신호를 보내지 않아 무한 대기했음. 시각 지정 방식은 기다릴 필요가 없어 더 단순함.

**보내는 내용과 대상.**
- 글 내용은 보내지 않고 글 id와 게시판만 보냄. 브라우저는 "새 글 N개"만 세고, 누르면 새로고침해 서버가 그린 목록을 받음. 기존 학습용 코드는 받은 제목을 HTML로 바로 넣어 XSS 위험이 있었음.
- 게시판 피드에는 그 게시판 글만, 내가 쓴 글은 나에게 보내지 않음. 수정과 삭제는 알리지 않음.

**연결 관리.**
- 브라우저가 연결을 끊으면 목록에서 지움.
- 25초마다 빈 주석을 보내 프록시가 조용한 연결을 끊지 않게 함.
- 서버를 끌 때 SSE 연결을 먼저 닫음. 열린 연결이 남아 있으면 서버 종료가 끝나지 않음.
- 단독 서버처럼 Change Stream을 지원하지 않는 DB에서는 알림만 끄고 서버는 정상 동작함.

**감수한 단점.**
- 서버가 여러 대면 각 서버가 Change Stream을 하나씩 엶. 서버 수만큼이므로 접속자 수보다 훨씬 적음.
- 연결 수 제한이 없음. 접속자가 아주 많아지면 서버당 연결 수 제한이나 별도 알림 서버가 필요함.

## 14. 채팅은 글 단위 1:1 문의방이고, 소켓도 HTTP 세션으로 인증함

**채팅방 모델.** 글 하나에 문의자 한 명당 방 하나임. (글, 문의자)에 고유 인덱스를 걸고, `$setOnInsert` upsert로 "있으면 그대로, 없으면 생성"을 한 번에 처리함. 동시에 두 upsert가 모두 생성을 시도하면 한쪽이 중복 키 에러를 받는데, 그때는 먼저 만들어진 방을 돌려줌.

**메시지 저장.** 메시지는 별도 컬렉션에 저장하고, 방에 들어오면 최근 50개를 보여줌. 방 목록 화면에서 방마다 마지막 메시지를 조회하지 않도록 방 문서에 마지막 메시지와 시각을 복사해 둠. 그 이전 메시지 보기는 아직 없음.

**소켓 인증.**
- socket.io 연결의 첫 요청에 HTTP와 같은 세션 미들웨어와 passport를 적용해, 쿠키로 로그인 유저를 찾음. 로그인하지 않은 연결은 거절함.
- 방에 들어갈 때마다 참여자인지 DB로 확인함. 메시지는 실제로 들어간 방에만 보낼 수 있음.
- 메시지는 저장을 마친 뒤 방 전체에 보냄. 화면에는 서버가 보내준 메시지만 그리므로, 저장에 실패한 메시지가 보이는 일이 없음.

**행동 이벤트.** 방이 처음 만들어질 때 `chat_request` 이벤트를 남김. "글을 보고 실제로 연락했다"는 가장 강한 관심 신호임. 인기 점수에는 아직 넣지 않았음. 넣으면 지금까지의 성능 측정과 비교 조건이 달라지므로, 점수 규칙을 바꿀 때 함께 검토함.

**감수한 단점.**
- 서버가 여러 대가 되면 같은 방의 두 사람이 다른 서버에 붙을 수 있음. 그때는 서버 간에 메시지를 전달하는 어댑터(예: Redis 어댑터)가 필요함.
- 메시지 전송 횟수 제한이 없음.
- 읽음 표시와 안 읽은 메시지 수가 없음.

## 15. 데이터 품질은 주기적 검사로 탐지하고, 고치는 것은 사람이 확인한 뒤에 함

**무엇을 검사하나.** 이 파이프라인에서 실제로 생길 수 있는 문제만 골랐음.

| 검사 | 왜 생기나 | 상태 |
|---|---|---|
| 공감 수, 댓글 수 어긋남 | 원본 저장과 숫자 증감이 별개의 쓰기라 그 사이에 서버가 죽으면 생김 | 경고 |
| 반복 조회 | 새로고침으로 조회수 부풀리기 | 경고 |
| 주인 없는 이벤트 | 브라우저가 보낸 노출의 글 id는 존재 여부를 확인하지 않음 | 경고 |
| 시계 오차 | 브라우저 시계가 틀렸거나 전송이 늦음 | 경고 |
| 통계 갱신 지연 | 통계 작업이 멈춤 | 실패 |
| 통계 정합성 | 집계 로직 버그나 늦게 저장된 이벤트 | 실패 |
| 결과 0건 검색어 | 문제가 아닌 참고 정보 | 참고 |

파이프라인 자체가 틀렸음을 뜻하는 검사는 "실패", 데이터에 이상이 섞였음을 뜻하는 검사는 "경고"로 구분했음.

**운영 방식.**
- 서버 안에서 10분마다 실행해 결과를 `dq_reports`에 저장하고, 기준을 넘으면 로그로 경고함. 결과는 30일 TTL 인덱스로 자동 삭제함. 원본 이벤트와 달리 다시 만들 필요가 없는 기록이라서임.
- 통계 갱신 지연은 통계 문서의 갱신 시각이 아니라 작업 실행 기록(`job_runs`)으로 판단함. 통계 문서만 보면 이벤트가 없는 시간대에 작업이 멈춘 것으로 잘못 판단함.
- 반복 조회는 10분 고정 구간으로 자른 근사치임. 구간 경계를 걸친 반복은 놓칠 수 있음. 비로그인 조회는 사람을 구분할 수 없어 제외함.

**평소 검사와 전체 검사.** 공감 수, 댓글 수 검사는 평소에는 최근 24시간 안에 공감, 공감 취소, 댓글, 댓글 삭제가 있었던 글만 확인함. 숫자는 이런 쓰기가 일어날 때만 어긋나기 때문임. 전체 글을 확인하면 검사 비용이 글 수에 비례해 늘었음(문제 해결 기록 7번). DB를 직접 고쳐 생긴 어긋남은 전체 검사 명령으로 잡음.

**자동으로 고치지 않는 이유.** 검사 로직에 버그가 있으면 자동 수정이 멀쩡한 데이터를 망가뜨림. 바로잡기 명령은 기본으로 고칠 목록만 보여주고, `--apply`를 붙여야 실제로 고침. 고칠 때는 원본(likes, comments)을 정답으로 봄.

**감수한 단점.**
- 경고 기준값(반복 조회 20%, 주인 없는 이벤트 1%, 시계 오차 5%)은 가설임. 실제 트래픽에서 오탐과 미탐을 보며 조정해야 함.
- 탐지만 하고 인기 점수에서 이상 데이터를 걸러내지는 않음. 반복 조회를 점수에서 빼는 것이 다음 과제임.
- 서버가 여러 대면 각 서버가 같은 검사를 반복함.
